## 0. Scope

D054 introduces three identity layers and a minimum place layer, layered **on top of** the existing schema. Nothing is replaced. Existing `/dna/*` web-app reads must continue to succeed unchanged.

**In scope (v0.0):**
1. **Role layer** — single enum-typed column on `profiles`: `returnee | anchor | ally | exploring`
2. **Affirmation layer** — new `affirmations` table; one-time witnessed acts; role-aware witness constraint for ally crossings
3. **Place layer** — `continent` + `country` (ISO 3166-1 alpha-3) on `profiles`, validated against existing reference tables

**Out of scope (deferred to later D054 iterations / D029 / D030):**
- region / state / city additions to the place hierarchy
- RLS policy authoring (sketched in §6, not finalized)
- Backfill of role values from existing `user_type` data (see §5 — defaulted to `'exploring'`)
- Edge functions, triggers, indexes beyond what's listed
- Mobile-app React Native Supabase client — belongs in the separate mobile repo, NOT this web-app repo (see §9)

---

## 1. Why each layer is separate

The existing schema already has several "role-ish" fields that mean different things; D054 must not collapse them:

| Existing field                | Layer                       | Keep as-is? |
|-------------------------------|-----------------------------|-------------|
| `user_roles.role` (app_role)  | Platform RBAC (admin/mod/user) | yes |
| `profiles.user_type`          | Web onboarding category (diaspora_professional/founder/ally) | yes |
| `profiles.roles TEXT[]`       | Denormalized cache of `user_roles` | yes |
| `profiles.professional_role`  | Job title (free text)       | yes |
| **`profiles.dna_role` (new)** | **D054 identity role**      | new |

A new dedicated column is preferred over extending `user_type` because:
- `user_type`'s CHECK list already includes `'ally'` — overloading it would make web-app code paths (which key off `user_type` for onboarding routing) silently break for `'returnee' | 'anchor' | 'exploring'`.
- Identity role is conceptually orthogonal to "what kind of user signed up" — a `founder` and a `diaspora_professional` can both be `returnee`s.
- Postgres ENUM gives us cheap referential safety vs. CHECK strings.

## 2. Open questions (resolve before running)

1. **Default role for existing rows** — plan defaults to `'exploring'` (passive, lowest-trust). Alternative: leave NULL and force re-onboarding to set it. Chosen `'exploring'` so existing users keep working without an interstitial.
2. **Self-witness** — disallowed by CHECK (a user cannot affirm themselves).
3. **Ally-witnesses-ally** — `affirmation_type = 'ally_crossing'` requires a witness whose role-at-time is `returnee` or `anchor`. Not `ally`, not `exploring`. Confirm this is the intended doctrine before applying.
4. **One-time semantics** — UNIQUE `(subject_user_id, affirmation_type)`. So a user can have at most one affirmation of each type. Confirm whether `affirmation_type` should be an enum (closed list) or free text (open extensibility); plan currently goes with enum for safety.
5. **Continent representation** — `continents` has no `code` column today, only UUID `id` and `name`. Plan uses FK by id. If we want a stable code (`AF`/`EU`/etc.) we'd add it to `continents` first; not done in v0.0 to keep scope tight.
6. **Place at profile vs. event level** — v0.0 scopes place to `profiles` only. Posts/events/spaces already have their own location fields; not touched.

## 3. Migration sequence

Each statement is enumerated. Run order matters (enum before column, columns before constraints).

### A. Role layer

#### A.1 — `CREATE TYPE public.dna_identity_role`

```sql
CREATE TYPE public.dna_identity_role AS ENUM (
  'returnee',
  'anchor',
  'ally',
  'exploring'
);
```

- **Rationale:** Closed set of identity roles per D054 doctrine. Enum (not TEXT+CHECK) so values are referentially safe and cheap to compare; downstream constraints in `affirmations` can also use this type.
- **Defaults:** N/A (type creation).
- **Web-app impact:** None. Type lives in `public` but is not referenced by any current column until A.2.

#### A.2 — `ALTER TABLE profiles ADD COLUMN dna_role`

```sql
ALTER TABLE public.profiles
  ADD COLUMN dna_role public.dna_identity_role NOT NULL DEFAULT 'exploring';
```

- **Rationale:** Single-source-of-truth column for D054 identity layer. NOT NULL with default avoids a backfill pass and avoids null-handling code in clients.
- **Default for existing rows:** `'exploring'`. Existing users start in the passive layer; they "graduate" by affirmation (§B).
- **Web-app impact:** Additive column only. Web app does not currently read `dna_role`. Web TypeScript types regenerated from Supabase will pick it up as an optional field on `Row`; no compile breaks. Auto-generated INSERT statements that explicitly enumerate columns continue to work because the column has a default.
- **Reversibility:** `ALTER TABLE profiles DROP COLUMN dna_role; DROP TYPE public.dna_identity_role;` (drops in reverse order).

#### A.2b — `ALTER TABLE profiles ADD COLUMN dna_identity_declared_at`

```sql
ALTER TABLE public.profiles
  ADD COLUMN dna_identity_declared_at timestamptz;
```

- **Rationale:** Gate column for BD008 (force role + place declaration on next login for
  pre-D054 users). The default for existing rows is **NULL**, which is exactly the signal
  the `OnboardingGuard` predicate keys off (see §11). Setting it requires an explicit
  declaration submit, even when the user picks `'exploring'`.
- **Default for existing rows:** NULL (no DEFAULT clause — we want NULL until declared).
- **Web-app impact:** Additive nullable column. Web app does not currently read it.
  Adding to the `OnboardingGuard` SELECT projection costs one column. Detail in §11.
- **Reversibility:** `ALTER TABLE profiles DROP COLUMN dna_identity_declared_at;`

#### A.3 — Optional: backfill from `user_type` (NOT scheduled for v0.0)

```sql
-- INTENTIONALLY COMMENTED OUT — leave for a follow-up migration after product confirms mapping
-- UPDATE public.profiles
--   SET dna_role = 'ally'
--   WHERE user_type = 'ally' AND dna_role = 'exploring';
```

- **Rationale:** Don't auto-promote anyone into a non-passive role on day 0. `user_type = 'ally'` in web onboarding ≠ a witnessed `'ally'` in D054 doctrine. Product decides the mapping later.

### B. Affirmation layer

#### B.1 — `CREATE TYPE public.dna_affirmation_type`

```sql
CREATE TYPE public.dna_affirmation_type AS ENUM (
  'arrival',
  'ally_crossing',
  'role_change',
  'witness'
);
```

- **Rationale:** Closed list of one-time witnessed acts. `arrival` = a user is affirmed into the network; `ally_crossing` = an ally moves into deeper participation (role-aware witness required); `role_change` = transition between non-ally roles; `witness` = generic affirmation by a peer. Confirm names with product before running.
- **Defaults:** N/A.
- **Web-app impact:** None until B.2 references it.

#### B.2 — `CREATE TABLE public.affirmations`

```sql
CREATE TABLE public.affirmations (
  id                     uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  subject_user_id        uuid NOT NULL REFERENCES auth.users(id) ON DELETE CASCADE,
  witness_user_id        uuid NOT NULL REFERENCES auth.users(id) ON DELETE RESTRICT,
  affirmation_type       public.dna_affirmation_type NOT NULL,
  subject_role_at_time   public.dna_identity_role NOT NULL,
  witness_role_at_time   public.dna_identity_role NOT NULL,
  note                   text,
  context                jsonb NOT NULL DEFAULT '{}'::jsonb,
  witnessed_at           timestamptz NOT NULL DEFAULT now(),
  created_at             timestamptz NOT NULL DEFAULT now()
);
```

- **Rationale:**
  - `subject_user_id` / `witness_user_id` reference `auth.users` (matches existing convention — `profiles.id` is the only FK to `auth.users` today; affirmations reference auth so they survive a profile rebuild, and CASCADE removes a user's affirmation history if they delete their auth account).
  - `*_role_at_time` are snapshotted (not joined) so an affirmation remains historically truthful after the subject or witness later changes role.
  - `context jsonb` carries structured metadata (event_id, place_id, narrative pointers) without schema churn.
  - `witnessed_at` separate from `created_at` so a witness can affirm an act that happened earlier.
- **Defaults for existing rows:** N/A — table starts empty.
- **Web-app impact:** New table. Web app does not read it. Zero backward-compat risk.
- **Reversibility:** `DROP TABLE public.affirmations; DROP TYPE public.dna_affirmation_type;`

#### B.3 — Self-witness prevention

```sql
ALTER TABLE public.affirmations
  ADD CONSTRAINT affirmations_no_self_witness
  CHECK (subject_user_id <> witness_user_id);
```

- **Rationale:** A user cannot affirm themselves. Witnessing is inherently external.
- **Defaults:** N/A.
- **Web-app impact:** None.

#### B.4 — One-time-per-type uniqueness

```sql
ALTER TABLE public.affirmations
  ADD CONSTRAINT affirmations_one_per_subject_type
  UNIQUE (subject_user_id, affirmation_type);
```

- **Rationale:** D054 says "one-time witnessed act." A subject has at most one affirmation per type. If the doctrine later needs multiple witnesses for the same act, drop this and replace with `(subject_user_id, affirmation_type, witness_user_id)`.
- **Defaults:** N/A.
- **Web-app impact:** None.

#### B.5 — Role-aware witness for ally crossings

```sql
ALTER TABLE public.affirmations
  ADD CONSTRAINT affirmations_ally_crossing_witness_role
  CHECK (
    affirmation_type <> 'ally_crossing'
    OR witness_role_at_time IN ('returnee', 'anchor')
  );
```

- **Rationale:** When an ally crosses into deeper participation, the witness must be someone with diaspora identity standing — not another ally, not someone still in the passive `exploring` state. Encodes the doctrine that ally legitimacy is granted by the community, not by other allies.
- **Defaults:** N/A.
- **Web-app impact:** None (web app doesn't INSERT affirmations).

#### B.6 — Lookup indexes

```sql
CREATE INDEX affirmations_subject_user_id_idx ON public.affirmations (subject_user_id);
CREATE INDEX affirmations_witness_user_id_idx ON public.affirmations (witness_user_id);
CREATE INDEX affirmations_witnessed_at_idx   ON public.affirmations (witnessed_at DESC);
```

- **Rationale:** Three primary read patterns — affirmations *received by* a user, affirmations *given by* a user, recent affirmations feed. Composite indexes deferred until query patterns harden.
- **Defaults:** N/A.
- **Web-app impact:** None.

### C. Place layer (continent + country alpha-3)

The existing schema already has rich place data. v0.0 adds **two** authoritative columns on `profiles` so D054 reads/writes have a single, validated source of truth — without disturbing the legacy fields the web app already uses.

#### C.1 — `ALTER TABLE profiles ADD COLUMN dna_country_iso3`

```sql
ALTER TABLE public.profiles
  ADD COLUMN dna_country_iso3 char(3);
```

- **Rationale:** Authoritative ISO 3166-1 alpha-3 country code. Separate from the existing `current_country_code` (length not enforced, alpha-2 vs alpha-3 ambiguous, no FK), `current_country_id` (UUID FK — opaque), `country_of_origin` (free text), and `country_origin` (duplicate free text).
- **Default for existing rows:** NULL. Existing rows are not auto-mapped because `current_country_code` may be alpha-2 in some rows and alpha-3 in others; safer to backfill in a follow-up scripted job after audit.
- **Web-app impact:** Additive nullable column. Web app continues to read its existing `current_country_*` columns unchanged.

#### C.2 — Validate `dna_country_iso3` against `countries.country_code_iso3`

```sql
ALTER TABLE public.profiles
  ADD CONSTRAINT profiles_dna_country_iso3_valid
  CHECK (
    dna_country_iso3 IS NULL
    OR dna_country_iso3 ~ '^[A-Z]{3}$'
  );
```

- **Rationale:** Cheap format guard (uppercase alpha-3). A full FK to `countries(country_code_iso3)` is preferred but requires `country_code_iso3` to have a UNIQUE index — verify that's true on the live DB before promoting this to:
  ```sql
  -- preferred but conditional on a UNIQUE index existing on countries.country_code_iso3:
  -- ALTER TABLE public.profiles
  --   ADD CONSTRAINT profiles_dna_country_iso3_fkey
  --   FOREIGN KEY (dna_country_iso3) REFERENCES public.countries(country_code_iso3);
  ```
- **Default for existing rows:** Passes for NULL.
- **Web-app impact:** None.

#### C.3 — `ALTER TABLE profiles ADD COLUMN dna_continent_id`

```sql
ALTER TABLE public.profiles
  ADD COLUMN dna_continent_id uuid REFERENCES public.continents(id) ON DELETE SET NULL;
```

- **Rationale:** Continent at v0.0 is referenced by UUID FK because `continents` has no stable code column today (columns are `id`, `name`, `description`, `created_at`, `updated_at`). If product later wants a 2-char continent code (`AF`/`EU`/`NA`/`SA`/`AS`/`OC`/`AN`), that should be added to `continents` first as a separate migration, and `dna_continent_id` can be deprecated in favor of `dna_continent_code`.
- **Default for existing rows:** NULL. No auto-derive from `current_country_id → countries.region_id → regions.continent_id` in v0.0 — that's a follow-up backfill.
- **Web-app impact:** Additive nullable FK. Web app does not read it.

#### C.4 — Coherence (continent must match country, when both present)

```sql
-- DEFERRED to v0.1. Requires either:
--   (a) a denormalized continent_iso3 lookup table, or
--   (b) a trigger that resolves countries.country_code_iso3 → regions → continents on insert/update.
-- Skipped in v0.0 because a CHECK constraint cannot span tables and triggers add operational
-- complexity that needs product sign-off first.
```

- **Rationale:** Defer the cross-field coherence rule until product confirms whether continent should be auto-derived (trigger) or user-asserted (allowing intentional mismatch for diaspora cases).

## 4. Application order (transaction safety)

The migration should run as **one transaction** if possible, but the type creations (A.1, B.1) and the table create (B.2) cannot be inside the same DDL transaction as RLS policy creation on some Postgres versions — run RLS in a follow-up migration.

Recommended order:
```
A.1  CREATE TYPE dna_identity_role
A.2  ALTER profiles ADD dna_role
A.2b ALTER profiles ADD dna_identity_declared_at
B.1  CREATE TYPE dna_affirmation_type
B.2  CREATE TABLE affirmations
B.3  CHECK no_self_witness
B.4  UNIQUE one_per_subject_type
B.5  CHECK ally_crossing_witness_role
B.6  CREATE INDEX × 3
C.1  ALTER profiles ADD dna_country_iso3
C.2  CHECK dna_country_iso3 regex
C.3  ALTER profiles ADD dna_continent_id
```

## 6. RLS sketch (NOT applied in v0.0)

Drafts for the follow-up migration:

```sql
-- profiles.dna_role: read self + read of any profile already publicly visible per existing policies
-- No new policy needed if existing profiles SELECT policies cover the row;
-- new column inherits row-level visibility.

-- affirmations:
ALTER TABLE public.affirmations ENABLE ROW LEVEL SECURITY;

-- read: subject or witness can read their own affirmations; public-read TBD per doctrine
CREATE POLICY affirmations_read_own ON public.affirmations
  FOR SELECT USING (
    auth.uid() = subject_user_id OR auth.uid() = witness_user_id
  );

-- insert: witness must be the authenticated user, and role-at-time fields must reflect current state
CREATE POLICY affirmations_insert_as_witness ON public.affirmations
  FOR INSERT WITH CHECK (
    auth.uid() = witness_user_id
    AND witness_role_at_time = (SELECT dna_role FROM public.profiles WHERE id = auth.uid())
    AND subject_role_at_time = (SELECT dna_role FROM public.profiles WHERE id = subject_user_id)
  );

-- update / delete: not permitted (affirmations are append-only historical records)
```

Confirm read-policy doctrine before applying — affirmations may be intentionally public for community visibility.

## 7. Rollback

Each migration is reversible in reverse order:

```sql
-- C
ALTER TABLE public.profiles DROP COLUMN dna_continent_id;
ALTER TABLE public.profiles DROP CONSTRAINT profiles_dna_country_iso3_valid;
ALTER TABLE public.profiles DROP COLUMN dna_country_iso3;

-- B
DROP INDEX public.affirmations_witnessed_at_idx;
DROP INDEX public.affirmations_witness_user_id_idx;
DROP INDEX public.affirmations_subject_user_id_idx;
DROP TABLE public.affirmations;
DROP TYPE public.dna_affirmation_type;

-- A
ALTER TABLE public.profiles DROP COLUMN dna_identity_declared_at;
ALTER TABLE public.profiles DROP COLUMN dna_role;
DROP TYPE public.dna_identity_role;
```

Rollback is safe only as long as no D054 client code has begun writing to these columns/tables. Once production traffic depends on `dna_role`, rolling back drops live data.

## 9. Mobile React Native client — out of scope here

The original task asked for a `lib/supabase.ts` configured for React Native (AsyncStorage, `detectSessionInUrl: false`). This repo is the **web app** at `diasporanetwork.africa/dna/*` — Vite + React + `window.localStorage` — not an Expo/RN project. Creating that client here would either:
- break the Vite build (`@react-native-async-storage/async-storage` doesn't resolve under web bundlers), or
- ship a dead file that desyncs auth storage keys with the existing web client.

**Where it belongs:** in the separate DNA mobile repo (Expo). The shape it should take, given the schema in this plan:

```ts
// mobile-repo/lib/supabase.ts
import 'react-native-url-polyfill/auto';
import AsyncStorage from '@react-native-async-storage/async-storage';
import { createClient } from '@supabase/supabase-js';
import type { Database } from './database.types'; // generated via `supabase gen types`

export const supabase = createClient<Database>(
  process.env.EXPO_PUBLIC_SUPABASE_URL!,
  process.env.EXPO_PUBLIC_SUPABASE_ANON_KEY!,
  {
    auth: {
      storage: AsyncStorage,
      autoRefreshToken: true,
      persistSession: true,
      detectSessionInUrl: false,
      storageKey: 'dna-mobile-auth-token', // distinct from web's 'dna-auth-token'
    },
  },
);
```

Notes for the mobile-repo author:
- Use the same Supabase URL/anon key as the web app (project `ybhssuehmfnxrzneobok`) — same backend, same RLS, same `auth.users`.
- Use a **different `storageKey`** than the web app's `'dna-auth-token'` so the two clients can't accidentally clobber each other's tokens during local dev.
- Regenerate `database.types.ts` after the D054 migrations land, so mobile picks up `dna_role`, `affirmations`, etc.

## 11. Existing-user migration flow (BD008)

BD008 requires that **every user who pre-dates D054 must declare a DNA role and a DNA × Place
on their next login**, with `'exploring'` available as the soft opt-out so no user is hard-blocked.

The defaults in §3 (`dna_role` = `'exploring'`, `dna_country_iso3` = NULL,
`dna_continent_id` = NULL) keep existing rows technically valid, but the **app must treat
those defaults as "not yet declared"** until the user explicitly affirms them through a
new UI step. The mechanism below adds the gating predicate without re-flowing existing
users through the full 5-step onboarding wizard.

### 11.1 New "declared" timestamp on `profiles`

Add a single timestamp column the gating logic can key off:

```sql
ALTER TABLE public.profiles
  ADD COLUMN dna_identity_declared_at timestamptz;
```

- **Default for existing rows:** NULL. All pre-D054 users have NULL on their first
  post-migration login, which is exactly the signal the guard needs.
- **Set to:** `now()` when the user submits the new "Declare your DNA" step
  (regardless of whether they chose `'exploring'` or a substantive role —
  the choice is what they declared, and `'exploring'` is a legitimate choice).
- **Backward-compatibility:** additive nullable column; nothing reads it today.

> Alternative considered and rejected: gate off `dna_role IS NOT NULL`. Rejected
> because we want the column to remain NOT NULL with a meaningful default (so RLS,
> joins, and analytics never have to null-check it), and because `'exploring'` is
> a valid declared state, not the absence of one.

### 11.2 Gating logic — where it lives

The check belongs in **`src/components/auth/OnboardingGuard.tsx`**, alongside the
existing `onboarding_completed_at` check. It is the only place every protected route
already funnels through (per `App.tsx` route wrappers), and it already runs a small
`useQuery` against `profiles` on each guarded navigation — adding two more columns to
that SELECT costs nothing.

**Proposed change** (sketch only — not applied in this cycle):

```ts
// src/components/auth/OnboardingGuard.tsx
const { data: profile } = useQuery({
  queryKey: ['onboarding-check', user?.id],
  queryFn: async () => {
    const { data } = await supabase
      .from('profiles')
      .select('onboarding_completed_at, username, dna_identity_declared_at')  // +1 column
      .eq('id', user.id)
      .single();
    return data;
  },
  enabled: !!user?.id,
});

useEffect(() => {
  if (authLoading || profileLoading) return;
  if (!user) { navigate('/auth', { replace: true, state: { from: location.pathname } }); return; }

  const hasCompletedOnboarding = !!(profile?.onboarding_completed_at || profile?.username);
  const hasDeclaredIdentity   = !!profile?.dna_identity_declared_at;

  // Step 1: brand-new users → /onboarding (unchanged)
  if (!hasCompletedOnboarding && location.pathname !== '/onboarding') {
    navigate('/onboarding', { replace: true });
    return;
  }

  // Step 2 (NEW): completed onboarding but pre-date D054 → /onboarding/declare
  if (hasCompletedOnboarding && !hasDeclaredIdentity
      && location.pathname !== '/onboarding/declare') {
    navigate('/onboarding/declare', { replace: true });
    return;
  }

  // Existing: completed everything but on /onboarding → push to discover
  if (hasCompletedOnboarding && hasDeclaredIdentity && location.pathname === '/onboarding') {
    navigate('/dna/connect/discover', { replace: true });
  }
}, [profile, user, authLoading, profileLoading, navigate, location.pathname]);
```

### 11.3 The declaration screen `/onboarding/declare`

Lean, single-screen. **Not** a re-run of the 5-step wizard.

- **Field 1 — DNA role** (required). Four options matching `dna_identity_role`:
  - **Returnee** — has returned / will return
  - **Anchor** — committed to building on the continent
  - **Ally** — supporter from the diaspora periphery (note: this is the D054 role, *not* the legacy `user_type='ally'`)
  - **Still exploring** — the soft option per BD008; the user can advance without committing
- **Field 2 — DNA × Place** (required):
  - **Continent picker** (single-select, populated from `continents`) → writes `dna_continent_id`
  - **Country picker** (single-select, populated from `countries` filtered by continent → ISO-3) → writes `dna_country_iso3`
  - If the user picks `'exploring'` as their role, the country picker can be left blank (NULL) — but `dna_identity_declared_at` is still set on submit.
- **Submit handler:**
  ```ts
  await supabase.from('profiles').update({
    dna_role,
    dna_country_iso3,
    dna_continent_id,
    dna_identity_declared_at: new Date().toISOString(),
  }).eq('id', user.id);
  await refreshProfile();  // AuthContext exposes this
  queryClient.invalidateQueries({ queryKey: ['onboarding-check', user.id] });
  navigate('/dna/feed', { replace: true });
  ```

### 11.4 Route registration

Add a single new route in `App.tsx` near line 314 (the existing un-guarded `/onboarding`):

```tsx
<Route path="/onboarding/declare" element={<DeclareIdentity />} />
```

- **Not** wrapped in `OnboardingGuard` (same reason `/onboarding` isn't — would cause an
  infinite redirect).
- Should itself check `useAuth().user` and redirect to `/auth` if absent.

### 11.5 Brand-new (post-D054) users

For users who sign up **after** the migration lands, the cleanest path is to fold the
declaration into the existing 5-step wizard rather than send them through `/onboarding`
+ `/onboarding/declare` back-to-back. Options:

- **Option A (recommended): insert a new sub-step into `UserTypeStep`** that captures
  `dna_role` alongside `user_type`. The two are conceptually adjacent (both are
  "who are you on this platform") and combining them avoids the user feeling like
  they answered the same question twice.
- **Option B:** add a sixth step to the wizard before the username step. Simpler code
  change but worse UX (one more click).

In either option, the final UPSERT at the end of `Onboarding.tsx` writes
`dna_role`, `dna_country_iso3`, `dna_continent_id`, **and**
`dna_identity_declared_at = now()` alongside `onboarding_completed_at`. New users then
never see `/onboarding/declare` because the guard predicate is already satisfied.

### 11.6 Edge cases to confirm with product

1. **Can a user change their declared role later?** The migration plan has
   `affirmations` as one-time-per-type (§B.4). The `dna_role` column itself is
   mutable (no constraint blocks UPDATE), but the UI surface for changing it is
   undefined — propose Settings → Identity, gated by a confirmation modal.
2. **Does `'exploring'` reset to non-`'exploring'` later require a witness?** Per the
   doctrine sketch, yes — that transition is the `'arrival'` affirmation. The
   `'exploring'` → `'ally'` transition specifically is the `'ally_crossing'` affirmation
   and requires a `returnee`/`anchor` witness (§B.5).
3. **What happens if a user declines to pick a country?** `'exploring'` + NULL country
   is permitted. Any other role + NULL country is **also** permitted at the column
   level today; the UI should require it for `returnee`/`anchor`/`ally` and let it
   slide for `'exploring'`. (Enforcing this at the DB level would need a CHECK
   constraint — deferred until product confirms the rule.)
4. **Re-declaration after an admin role change.** Out of scope — admin role
   (`app_role`) is independent of `dna_role`.
